Making changes to igvbuild.com without Sarah

This site is plain HTML, CSS and JavaScript — no build framework, nothing to "compile." If you can edit a text file, you can edit this site. This guide covers how GitHub works, and how this specific site is put together.

Part 1 GitHub basics

What GitHub actually is

Repository ("repo") — the project folder, tracked by Git, with a full history of every change ever made. This site's repo is IGV-Housing/igvbuild-website.

Commit — a saved snapshot of changes, with a short message explaining what changed and why.

Push — uploads your commits to GitHub, where they become visible to everyone and (see Part 5) go live on the site.

Pull — downloads the latest commits down to your computer. Always pull before you start editing, so you're working from the latest version, not an old copy.

Branch — a parallel, independent copy of the codebase you can commit to without affecting anything else, until it's merged back in.

main branch — the live, production version of the site. Whatever is on main is what visitors see. Nobody pushes directly to main.

staging branch — where everyone does their day-to-day work. You pull, edit, commit, and push here. Sarah reviews what's on staging and merges it into main manually when it's ready to go live, so main never receives unreviewed changes.

Getting set up (one-time)

  1. Create a free account at github.com and ask to be added as a collaborator on IGV-Housing/igvbuild-website.
  2. Install GitHub Desktop — a free app that handles every Git step below with buttons, no command line required.
  3. Install VS Code (or any text/code editor) to actually edit the files.
  4. In GitHub Desktop: File → Clone Repository, search for IGV-Housing/igvbuild-website, and pick a folder on your computer. This downloads the whole site.
  5. In GitHub Desktop's branch switcher (top middle of the window), switch from main to staging. This is the branch you'll work on from now on — check it any time you're not sure which branch you're on.

The everyday workflow

  1. Open GitHub Desktop, confirm the branch switcher says staging (switch to it if not), then click Fetch origin and Pull origin if there's anything new — never start editing an old copy.
  2. Open the project folder in VS Code and make your edits (Part 2 covers how the site is structured).
  3. Preview the change locally before pushing (Part 3) — never push something you haven't seen rendered in a browser.
  4. Back in GitHub Desktop, review the diff for every changed file — if something's there you didn't mean to touch, stop and look into it.
  5. Write a clear commit message ("Update Contractors hero copy," not "changes"), then Commit to staging.
  6. Click Push origin. Your change is now on the staging branch on GitHub. It is not live yet — Sarah reviews staging and merges it into main when it's ready, which is what actually publishes it (Part 5).

Rules of thumb

Nevercommit or push directly to main — always work on staging. Check the branch switcher before you commit.
Never"Discard changes" a file unless you're certain you want that work gone for good.
Neverforce-push or delete either branch. Stop and ask if GitHub Desktop shows a conflict you don't understand.
Before pushingpreview locally and, for anything visual, get a second pair of eyes on a screenshot.

Part 2 How this site is built

File map

igvbuild/ index.html, howitworks.html, contractors.html, ... one file per page igvhomescatalogue/ osprey/index.html, summit/index.html, ridgeline/index.html css/ style.css the real, readable stylesheet — edit this one style.min.css compressed copy every page actually loads js/ main.js the real, readable script — edit this one main.min.js compressed copy every page actually loads images/ every image, logo and icon on the site

The most important quirk: there's no shared template

Because this is plain HTML with no build tooling, the navigation bar, the mega-menu dropdowns, and the footer are copy-pasted into every single HTML file. There's no shared header.html the pages all pull from.

⚠ A change to the nav or footer — a new page link, an updated copyright year — has to be made in all ~14 HTML files, not just one. Search-and-replace across files is far more reliable than editing each file by hand. This is exactly the kind of repetitive, error-prone task an AI coding assistant handles well — describe the change once and ask it to apply it everywhere.

Editing text, images, or styles

Text/content — open the relevant .html file and change the words between the tags. Tags like <h1>, <p>, <a> are structure — don't delete or rearrange them, just the text inside.

Images — drop the new file into images/, then update the matching src="images/your-file.jpg". See the image guidelines below before you upload anything.

Styles — all visual styling (colors, spacing, fonts, mobile layout) lives in css/style.css, organized in sections by component. Search for the relevant class name, e.g. .footer, .contractors-hero, .mega-grid.

Part 3 Previewing changes locally

Don't push a change you haven't seen rendered in a browser. There's no build step, so previewing is simple:

Quickest

Just double-click the .html file to open it in your browser. Works for most content and text edits.

More accurate

Needed for anything that depends on the page being served over http:// rather than opened as a raw file. Install Node.js once, then from the project folder:

npx serve .

Open the printed localhost address. Check both a normal desktop window and a narrow mobile-width window (browser dev tools → toggle device toolbar) — most past bugs on this site were mobile-only layout issues invisible at desktop width.

Part 4 CSS/JS minification — don't skip this

Every page's <link>/<script> tag points at style.min.css and main.min.js — not the readable source files.

⚠ If you edit style.css or main.js and don't regenerate the .min versions, your change will not appear on the live site — even though the source file looks correct. This is the single most common way a change silently "doesn't work."

Regenerate both after any CSS/JS edit (requires Node.js installed once):

npx clean-css-cli -O2 -o css/style.min.css css/style.css
npx terser js/main.js -o js/main.min.js -c -m --comments false

Run from the project's root folder, re-check the site locally, then commit both the source file and its regenerated .min file together, in the same commit.

Image guidelines

Learned the hard way during a site-wide performance pass — keep these in mind for any new image:

  • Format — JPG for photos, PNG only when you genuinely need transparency (a cutout graphic, a logo with no background). A photo saved as PNG is often 5–10× larger than the same photo as JPG, for no visual benefit.
  • Size — resize to roughly the largest size it'll actually display at before uploading. Don't drop a 5000px-wide camera photo in for a 400px-wide thumbnail.
  • Clean up after yourself — if you replace an image, delete the old file once you've confirmed nothing else references it: grep -r "old-filename" *.html from the project root will tell you.

Getting help

If something goes wrong — a merge conflict, an accidental push you want to undo, a "detached HEAD" message you don't understand — stop and ask rather than clicking through prompts you're unsure about. Most Git mistakes are recoverable if caught early, and much harder to fix once several more commits pile on top.
